# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

libhddvd is an experimental C99 library (plus small CLI tools) for inspecting HD DVD
discs and Advanced Content (HDi) menus. The long-term goal is a VLC-drivable menu engine,
but libhddvd itself must stay independent of VLC, graphics APIs, codecs, and any particular
JavaScript engine. The only external dependency is libxml2.

## Commands

```sh
# Configure, build, run all tests
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure

# Run a single test (CTest names are the bare suffixes: core, aca, xpl, xmu, player, ...)
ctest --test-dir build -R '^xpl$' --output-on-failure
./build/test-xpl            # or run the test binary directly

# Format check exactly as CI does (CI pins clang-format 20.1.8: pip install clang-format==20.1.8)
find include src tests tools -type f \( -name '*.c' -o -name '*.h' -o -name '*.cpp' \) \
  -print0 | xargs -0 clang-format --dry-run --Werror
# Apply formatting: replace `--dry-run --Werror` with `-i`
```

Useful CMake options: `HDDVD_BUILD_SHARED` / `HDDVD_BUILD_STATIC` (both ON by default; at
least one is required), `HDDVD_SCRIPT_ENGINE` (`auto`/`quickjs`/`none`) with `HDDVD_QUICKJS_SOURCE_DIR` (an unpacked
QuickJS release compiled into libhddvd; `tools/fetch_quickjs.sh DEST` downloads the pinned,
checksummed one outside the tree; installed distribution `libquickjs.a` builds are not `-fPIC`,
so only static-only builds can use them),
`HDDVD_BUILD_FUZZERS` (Clang only; builds `fuzz-{aca,object,xmf,xmu,script,xpl,navigation,timemap,uri,titlemap,display,vts,titles}` (`fuzz-vts` also runs its input through the command VM; `fuzz-titles` replaces one file of a synthetic disc and reads `tests/fixtures/standard`), plus `fuzz-runtime` with an engine,
against `hddvd_fuzz`, a coverage-instrumented static copy of the library; fuzz with a scratch
copy of the seeds, because libFuzzer writes new inputs into the corpus directory it is given),
`HDDVD_ENABLE_REFERENCE_TESTS` and `HDDVD_ENABLE_EXTERNAL_MENU_TESTS` (opt-in Python tests that
read external data from `HDDVD_REFERENCE_ACA` / `HDDVD_EXTERNAL_MENU_CORPUS` and exit 77 =
skipped when unset; `HDDVD_EXTERNAL_MENU_STRICT=1` also fails on unmodeled XPL constructs).
Fixtures in `tests/fixtures/objects`, `tests/fixtures/scripts`, `tests/fixtures/timemap`, `tests/fixtures/hdi-api`, `tests/fixtures/standard` (a Standard Content disc under `standard/HVDVD_TS`), `tests/fixtures/app` (an ACA application and playlist for `hddvd-menurun`, and hand-written interaction traces for `tests/replay_reference_trace.py`) and the fuzz seeds in `tests/fixtures/fuzz` are generated by
`tests/fixtures/generate_objects.py`; edit the generator and rerun it rather than editing bytes.

CI (`.github/workflows/ci.yml`) runs the format check, a Linux/macOS/Windows build+test
matrix (shared+static, static-only, shared-only; Linux and the jobs below build QuickJS in,
macOS and Windows build without an engine), an ASan+UBSan build with Clang, a
ThreadSanitizer run (`test_threads.c` uses separate objects concurrently; `test_menu_threads.c` is a mock player host around one menu session), the Clang static
analyzer (`scan-build --status-bugs`), a 32-bit build (`cmake/toolchains/linux-i386.cmake`),
an ABI check on pull requests (`tools/abi_check.sh` allows only additions), and a libFuzzer
job that builds every harness and replays the seeds in `tests/fixtures`. The
scheduled `.github/workflows/fuzz.yml` runs each harness for ten minutes nightly. The
`install-consumer` CTest installs the library to a temp prefix and builds `tests/consumer/`
(C, C++17, and static variants) against the installed CMake package, so it catches
header/export/packaging regressions; it is slow (up to 600s timeout).

## Code conventions

- Allman braces, 4-space indent, 100-column limit (`.clang-format`). CI fails on any diff.
- Library code compiles with `-Wall -Wextra -Wpedantic -Wconversion -Wshadow` (`/W4` on MSVC);
  `-Wconversion` means size/offset narrowing must be explicit and checked.
- Every public function is declared `HDDVD_API` in the single public header
  `include/hddvd.h`; symbols are hidden by default. Shared-library builds define
  `HDDVD_BUILD_SHARED` (dllexport) and consumers get `HDDVD_USE_SHARED` (dllimport).
- Tests are plain `main()` programs using `assert`; CMake compiles them with `-UNDEBUG`
  so asserts (which also perform setup) run in Release builds. Tests needing files from
  `tests/fixtures` get the path via the `HDDVD_FIXTURE_DIR` compile definition, which is
  set per target in `CMakeLists.txt`.

## Adding things

- **New source file:** add it to `HDDVD_SOURCES` in `CMakeLists.txt`.
- **New test:** create `tests/test_<name>.c` and add `<name>` to the `foreach(test ...)` list
  in `CMakeLists.txt`; add a `HDDVD_FIXTURE_DIR` definition if it reads fixtures.
- **New tool:** add to the `foreach(tool ...)` list and to the `install(TARGETS ...)` list.
- **Version bump:** keep `project(... VERSION)` in `CMakeLists.txt`, the
  `HDDVD_VERSION_*` macros in `include/hddvd.h`, `hddvd_version()` in `src/hddvd.c`,
  and the version-string asserts in `tests/test_core.c` and `tests/consumer/consumer.c`
  in sync (plus the README heading/`find_package` example).

## Architecture

Layered, bottom-up (see `docs/HDI_MENU_IMPLEMENTATION_PLAN.md` for the full design):

1. **Context & errors** (`hddvd.c`, `limits.c`, `internal.h`): `hddvd_ctx` holds the disc
   root, log callback, last-error detail, and a `hddvd_config_limits`. Context-bound
   operations report failures through `hddvd_ctx_set_error` (status, subsystem, URI,
   offset, message) and a later success clears it. All functions return `hddvd_status`
   codes (`HDDVD_OK` = 0, negatives for errors); `hddvd_strerror` must cover every code.
2. **Streams** (`io.c`, `stream.c`): opaque, refcounted `hddvd_stream` with 64-bit
   `read_at`. File, memory, and slice streams; ACA member streams retain their backing
   archive stream and outlive the `hddvd_aca` handle.
3. **Disc/resource resolution** (`disc.c`, `uri.c`, `resource.c`): directory discovery,
   canonical `file:///dvddisc/...` URIs, and case-insensitive lookup that rejects
   traversal, encoded separators, ambiguous matches, and (POSIX) symlinks.
4. **ACA archives** (`aca.c`): native `HDDVDACA` reader with strict directory/CRC
   validation; path-based functions are compatibility wrappers over the handle API.
5. **Object envelopes** (`object.c`): validates and strips both the synthetic `HDDVDOBJ`
   envelope and the on-disc `AACS` envelope (283-byte header; clear types `0x02` image and
   `0x12` text, everything else protected), returning typed payloads. The XML parsers unwrap
   either via `hddvd_object_unwrap` (`internal.h`). It never attempts decryption;
   protected content goes through an explicit host `hddvd_decrypt_fn` provider or fails
   with `HDDVD_EPROTECTED`. Format notes: `docs/formats/`.
6. **Immutable XML models** (libxml2): `xpl.c` (playlists/titles/clips/apps), `xmf.c`
   (manifests), `application.c` (manifest + resolved dependencies), `xmu.c` (markup tree),
   `style.c` (specified/computed styles, image-for-state, z-order, navigation; further
   properties in `hddvd_xmu_get_style_details`, unknown ones reported as unmodeled).
7. **Scripts** (`runtime.c`, `runtime_dom.c`, `runtime_player.c`, `runtime_bridge.c`, `hdi_prelude.js`, `script_engine.h`,
   `script_quickjs.c`/`script_none.c`, `script_decode.c`): disc scripts are ECMAScript 3
   source (UTF-16BE), bare or in the clear `AACS` envelope; protected ones are encrypted.
   `hddvd_runtime` runs them in a sandboxed engine with heap, recursion, operation and time
   budgets. `runtime.c` and `runtime_dom.c` are engine-neutral (they share
   `runtime_internal.h`); only they include `script_engine.h`, behind which one backend is
   compiled (`docs/decisions/0001-script-engine.md`). `HDDVD_FEATURE_SCRIPT_RUNTIME` is set
   only with an engine. The HDi host objects (`document`, elements' state and style,
   `application` listeners, events, timers, animations) are JavaScript in
   `src/hdi_prelude.js`, embedded at build time by `cmake/EmbedFile.cmake`, over natives in
   `runtime_dom.c`, which keeps the focus and script state/style values and applies style
   values to a private `hddvd_xmu_styles` through `style.c`'s override hooks
   (`internal.h`). The runtime makes no callbacks; hosts call key/advance/dispatch and
   read focus, generation and issues. `Player`, `Diagnostics`, the application lifecycle
   and failing stubs for file, XML, network and storage objects are in the same prelude
   over `runtime_player.c`, which keeps the borrowed playlist, the player state and
   application list the host reports, and a bounded queue of typed commands the host
   takes and acknowledges. Markup timing (`<timing>` par/cue containers, set/animate/event
   actions, an XPath subset) also runs in the prelude; its values go to timing layers in
   `runtime_dom.c` that sit below script values. `runtime_bridge.c` runs a runtime as navigation-queue tasks
   (`hddvd_runtime_bridge_event`: scheduler events become key, clock and player events,
   and commands go to the host and come back as `HDDVD_EVENT_SCRIPT_ACK`). `docs/hdi-host-api.md` lists what discs use
   (`tools/inventory_hdi_scripts.py`) and `hddvd-menurun` runs a disc application. `script_decode.c` is a bounded structural
   decoder for the clean-room `HDIS` fixture format only, which is not a disc format.
8. **Display list** (`display.c`, `scene.c`): renderer-neutral, damage-tracked quads from a
   scene tree; images are decoded by a host callback into premultiplied RGBA (no built-in
   image decoder). Includes letterbox transforms and hit testing. `hddvd_scene_build` turns
   markup and computed styles into that scene tree (geometry, visibility, opacity, z-order,
   focus images, `<object>` images), fetching image bytes through a host callback, plus
   per-node decorations (background fill, text, image placement).
   `hddvd_display_build_scene` turns those into fill/image/text items
   (`hddvd_display_get_item`); the older quad accessors still list image quads only.
9. **Navigation scheduler** (`player.c`): `hddvd_nav` event queue, timers on title time
   (`hddvd_time`, 90 kHz), discontinuity/seek handling, and host command callbacks.
   `hddvd_menu` (`menu.c`) is the session a player's overlay code drives: it loads an
   application from the disc and joins runtime, scheduler, bridge, scene and display list
   (keys, pointer through the letterbox transform and hit test, `hddvd_menu_update` for the
   damage-tracked list, polled commands). `test_menu_threads.c` is its mock host under TSan.
10. **Probes and time maps** (`evo.c`, `ifo.c`, `vti.c`, `map.c`, `title_map.c`, `titles.c`, `std_nav.c`, `vts.c`, `vm.c`): EVO
    program-stream probing; IFO/VTI/MAP header validation; the VTI's EVOB table
    (`hddvd_vti`) and MAP time maps (`hddvd_tmap`). `hddvd_title_map` joins a playlist
    title's primary clips to their maps and VTI, so a title time resolves to an EVO URI and
    sector. Playlist `60fps` time counts at 60000/1001. Standard Content title sets
    (`hddvd_vts`: chapters, PGCs, cells, raw commands, time maps, cell addresses, VOBU map)
    and the VMG title table (`hddvd_vmg`); menu PGC unit tables in both and the VMG's
    first-play PGC; `vm.c` runs navigation commands (`hddvd_vm_run`, libdvdnav semantics,
    64 GPRMs) and reports the link or jump for the host to follow; stream attributes in title sets and VTIs;
    `hddvd_titles` (`titles.c`) lists a disc's playable titles, Standard Content from the VMG or
    Advanced Content from a playlist (`hddvd_open_playlist` finds it), and reads a title's
    extents as one program stream, refusing scrambled (AACS) packets with `HDDVD_EPROTECTED`
    unless a host sector provider (`hddvd_titles_set_sector_provider`) supplies the clear sector;
    `hddvd_std_nav` (`std_nav.c`) follows a Standard Content disc's first play, menus, jumps and
    links through the VM to the cell to play (libdvdnav's rules; what it does not model ends
    in an explicit step); `hddvd-titles` lists, reads and navigates;
    `hddvd-vtsinfo` disassembles commands (DVD-Video encoding) and checks them and the
    tables against an EVO's navigation packs and streams (`docs/formats/ifo-map.md`).

Capability negotiation: hosts call `hddvd_abi_version()` and `hddvd_get_features()`.
Only set a feature bit when the capability is actually implemented.

### Limits and ABI rules

- Every parser is bounded. The unified `hddvd_config_limits` (`limits.c`) is the canonical
  set; older per-subsystem structs (`hddvd_limits`, `hddvd_xmf_limits`, ...) and their
  `*_with_limits` entry points remain for ABI compatibility. New constructors follow the
  `foo_open` / `foo_open_with_limits` / `foo_open_with_config` pattern. Raise a limit by
  making it configurable, not by bumping a hard-coded constant.
- Preserve ABI within a released major version: add functions rather than changing
  signatures or public struct layouts. New public types should be opaque unless they are
  immutable value records.

## Project rules (from `docs/IMPLEMENTATION_TASKS.md`)

- Work is tracked as task IDs (e.g. P3-01) with status, dependencies, and acceptance
  criteria in `docs/IMPLEMENTATION_TASKS.md`; update the task's status when completing it.
  P4-06 (reference conformance) and P5-04 are blocked on a conforming-player trace;
  `docs/REFERENCE_TRACE.md` says how to record one, and `tests/replay_reference_trace.py`
  replays it against `hddvd-menurun --state` (the `replay-*` and opt-in `reference-trace` CTests).
- A task is complete only when API docs, positive and negative tests, fuzz coverage where
  applicable, and `hddvd_strerror` behavior land in the same change.
- **Never commit, copy, or download the reference ACA or any external menu corpus** into
  the source or build tree. Fixtures under `tests/fixtures` must be original synthetic
  data (e.g. `tests/fixtures/generate_objects.py` regenerates the `.hdo` envelope
  fixtures); `test_aca.c` builds its archive at runtime.
- Production code must not special-case reference-menu filenames, element IDs,
  coordinates, or expected actions.
